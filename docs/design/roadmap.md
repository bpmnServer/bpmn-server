## Task templates (element templates)

**Hidden in 3.7.1** (`ELEMENT_TEMPLATES=on` shows them): the code, its tests (`test/ui/templates.test.mjs`,
`test/web/templates.test.mjs`) and the sample apps' templates (`connectors/*.json`) stay as they are.

A template is a configured task a designer picks in the model editor (Camunda 7's element template format): a
service task wired to a service, a user task for a group. Checked against what bpmn-server runs
(`packages/bpmn-web/src/routes/elementTemplates.ts`). To finish:

1. **See them in the editor:** the catalog, what each template sets, the templates left out and why (today only
   `GET /model/templates` says it).
2. **Where a value came from:** each property a template filled says *from template Manager approval*, the hidden
   ones too, and when the designer changed it.
3. **The `owf:` attributes:** `owf:assignmentPolicy`, `owf:actor`, `owf:notificationPolicy`, `owf:label`,
   `owf:endLabel`, `owf:exceptionsAsErrors`; and a business rule task's `camunda:resultVariable`,
   `camunda:mapDecisionResult`. A "Manager approval" template then carries its policy, its actor and its notices.
4. **A user task's form fields** (`camunda:formData`), if the template format allows it as we need.
5. **Its documentation:** a page (what they are, the file, an example per element, what is allowed and why, testing
   one), distinct from a notification policy's message templates.

## Tests of policies outside the editor

A policy's tests (the decision editor's Test tab, `<name>.policy.dmn.feature`) run in the editor, but an application's
own test runner (the HR demo's `npm test`) can't run them: `invokeDecision is not a function`. Next: the runner
evaluates a policy's tests as the editor does.

## An application's own facts, declared

The `decisionContext` hook adds names every table reads (`employeeManager`); nothing lists them, so the decision editor
can't offer them and a typo reads as `null`. Next: an application declares its facts (name, meaning), the editor offers
them, `verifyModel` checks them.

## With MDE-generated applications

An application generated by MDE (`@ai-mde/runtime`) knows its own design and says it over its API. Today's HR demo
does not: it began as the plain HR demo (`c:\mde\hrdemo.plain`, an Express server and `server/data.js`), not an
MDE application. Before the items below, decide: either the HR demo becomes an MDE application, or it answers the
same routes from its own data.

### The application's knowledge of itself (the meta API)

What the MDE runtime answers (`packages/runtime/src/http/routes.ts`, its `architecture.md`):

- `GET /model`: the entities, with each attribute's type, enum values, required and default; their references,
  states and transitions, operations and rules; the use cases (steps, actors); the pages; the roles with their
  titles; the authorization's grants.
- `GET /use-cases` and `GET /capabilities`.
- `/events/...`: the business events.
- `GET /work`: the caller's work items.
- `/help/...`: the online help, described in the next section.

What it can give us, in place of what an application declares by hand today:

- **Form keys** ([form-keys.md](form-keys.md)): the application's pages are in the model, so a form key can name
  one of them, and the model editor can offer them. This answers §8's question 1, where forms are registered.
- **Roles:** the model's roles, in place of `roles.json`.
- **Policies:** what a decision table may read (the entities' attributes, with their types and values), in place
  of an undeclared `decisionContext` (see *An application's own facts*, above).
- **Triggers:** a business event (an entity's transition) starts a process or a policy.

To settle:
- how bpmn-web reaches the application's model (a URL in the settings, read at start or when needed);
- whether `/work` and our task lists overlap;
- who may read `/model`.

### Help

An MDE application has a help system:
- `@ai-mde/help` (`ws/mdex/packages/help`);
- the application's `docs/` (`user-guide.md`, `walkthroughs/`, `capabilities/`);
- `GET /help/route?path=...` and `GET /help/page/<id>`;
- a React `HelpPanel` on the right of the page.

Our pages, the task form and the editors, would take part in it:
- the help of a task's page, from the model's documentation and the task's form fields;
- the user guide's section for a process.

Not started; noted only.

### Project assignment, in the HR demo

A workflow of several steps and actors:

1. The **project coordinator** (who coordinates several projects) records a need: the project, the skills, the
   dates.
2. The coordinator matches the need's skills to employees and proposes one.
3. The employee's **manager** approves the proposal.
4. The **employee** reviews it, agrees or not, and comments.
5. The **project manager** accepts the assignment, and the assignment is added.

It would use:
- the HR demo's employees, skills and projects;
- an assignment policy for each step (the employee's manager; the project's manager);
- notifications;
- the employee's comments kept on the case;
- a form key for the matching step (the application's assignment form).

`Assign Employee` today is service tasks only (read the employee, add the assignment). MDE's `c:\mde\hr` specified
the same domain: project matching, propose and approve, and the project assignment's states
(`docs/diagrams/state-project-assignment.md`).
